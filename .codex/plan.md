## Locked decisions for this ticket (sign these off)

**D-A · Capture contract = versioned Zod in `core/capture/contract.ts`, draft-permissive / resolved-strict.** `captureDraftSchema` mirrors §5 exactly: `version: z.literal(1)`, draft envelope fields, `ClarificationQuestion` (with the proposal ids it blocks), and `proposalSchema` as a **discriminated union on `kind`** over all 7 kinds — every proposal carries `intent`, `estimated`, `confidenceBps` (int 0–10000), `why{basis,assumptions}`, `occurredAt/localDate/timezone`, `evidenceRefs`, optional `matchedEntryId`; all quantities `z.number().int()` (paise/ml/minutes/grams/kcal). **Two layers:** the *draft* payload permits `null` exactly where “explicitly mentioned but quantity unknown” must be representable (water `millilitres: number|null` — required to validate the shipped canonical fixture, gate 9.2); the *commit input* `resolvedProposalSchema` is strict — non-null integers, resolution ids present, `status ∈ {auto, accepted}`. This reconciles §5 with the fixture without weakening any write path (a null quantity can never reach a repository). Recorded as part of **D-038** on sign-off (OQ-3). The contract must Zod-parse every §8 fixture relevant to SAR-004 before any parser/commit code lands.

**D-B · Routing policy = pure functions in `core/capture/route.ts`; the 9000 threshold lives only here.** `AUTO_WRITE_CONFIDENCE_BPS = 9000` and `ACCEPT_ALL_MIN_CONFIDENCE_BPS = 8000` are exported constants owned solely by this module. `routeProposal(proposal, draftQuestions)` → `{route:'auto'|'pending', reasons: readonly string[]}` implements §5.1 rules 3–4/7: `auto` **only if** `intent==='create'` ∧ `estimated===false` ∧ `confidenceBps>=9000` ∧ payload Zod-valid with all required integers non-null ∧ no unanswered clarification blocks it; **everything else `pending`** — every estimate, low-confidence explicit, correction, backdate, photo-derived, or question-dependent proposal. `routeDraft(draft)` partitions the draft. `applyUserEdit(proposal, patch)` → `estimated:false, confidenceBps:10000, why.basis:'user edit'` (rule 5). `isAcceptAllEligible(pending)` — all remaining `pending` ∧ all `>=8000` ∧ none question-blocked; still an explicit action (rule 6). Unknown unit/amount/date/category/habit/skill/match ⇒ pending question, **never an invented row** (rule 7). All functions pure and deterministic — no repo, no clock, no provider.

**D-C · Resolution precedes commit; auto demotes on resolution failure.** `core/capture/resolve.ts` turns routed proposals into `ResolvedProposal`s using the injected `UserScopedRepositories` (read-only lookups): exact case-insensitive name match against the user’s **active** habits/skills/categories. Non-nullable targets (`habitName→habitId`, `skillName→skillId`) that don’t resolve ⇒ the proposal is **demoted to `pending` with a question** (rule 7) — an auto-eligible proposal loses auto on failed resolution; nothing auto-creates a habit/skill. `categoryName` (**OQ-1 answered: hold §5.1 rule 7**): an unresolved category **demotes the transaction auto→pending with a question** — exactly like an unresolved habit/skill; nothing auto-files with an unknown category, and no category is silently created. (Consequence: the canonical fixture's explicit transaction auto-files only when its category resolves, so the route/commit tests seed the user's matching category — see step 4/6.) A `correction` resolves only if `matchedEntryId` is present, owned, kind-matching, and not soft-deleted; otherwise pending question. Direction mapping `expense→debit` / `income→credit` is fixed in the dispatch layer.

**D-D · `CommitService` = framework-clean core service with injected deps; one transaction; exhaustive typed dispatch.** Constructed as `createCommitService({repos, llm, now?})` (a composition root on the server side injects the concrete factory output and gateway — `core/` never imports them concretely). `commit({draftId?, idempotencyKey, kind, proposals: ResolvedProposal[]})`:
1. **Idempotency first:** `repos.commits.commits.list({idempotencyKey})` — an existing commit short-circuits and returns the original result **reconstructed from `commits` + `commit_rows` + effect rows** (no new columns, no migration; never duplicates rows or XP).
2. **Single-flight** (D-F), then **one `repos.transaction`** that: (a) marks the previous active batch (latest `committed`, not expired) `superseded` via `markSuperseded`; (b) creates the `commits` envelope (`status:'committed'`, `undoExpiresAt = now + 5min`, human `summary`); (c) runs `dispatchProposal` — an **exhaustive `switch` on `Proposal.kind`** (7 branches + `never` default) where each branch calls the matching typed repo: `transaction→money.transactions.create`, `meal→health.meals.create` (+ `health.mealItems.create` per item), `water→health.waterLogs.create`, `workout→health.workouts.create` (+ exercises), `weighIn→health.weighIns.create`, `habitLog→habits.logs.create`, `skillSession→skills.sessions.create`; `intent==='correction'` branches call `update(matchedEntryId, patch)` instead. **No `tableName`/generic payload path exists anywhere.** Entity `source:'capture'`, `estimated`/`confidenceBps` persisted from the resolved proposal; (d) writes one `commit_rows` snapshot per touched row (`create`: before null/after full; `update`: both); (e) computes deterministic XP/streak deltas via `core/game` pure functions, upserts `plans.progress` per touched domain, appends `commit_progress_effects`; (f) evaluates deterministic plan effects (plan items matching domain + localDate + rule → `done` with `completionSource:'capture'`), updates `plans.items`, appends `commit_plan_effects`; **(g) evaluates satisfied-by effects (acceptance item 4) — for each committed source row, checks the user's active `habits.satisfactionRules` and, when a rule's aggregate threshold is met for that `localDate`, auto-creates the matching `habits.logs` row (`status:'done'`, source marked satisfied-by) in the SAME batch (a normal typed row → undo reverses it via the create→softDelete path; it also produces a `commit_rows` snapshot and any progress effect like any other write)**; (h) writes evidence rows if the proposal carries evidence refs. With empty plan/rule tables (pre-SAR-009/SAR-012) steps (f)/(g) correctly record zero effects, but the writers **and their reversals** are complete now — build the pipeline once, so SAR-009 adds rules + a grid, not commit plumbing.
3. **After** the transaction commits: one capture `CoachNote` via fast-tier `llm.generateText({operation:'capture-line'})` → `repos.coach.notes.create({scope:'capture', stalenessKey: 'commit:'+commitId, …})`. Note failure is caught and reported in the result (`coachNote: null`) — **it never rolls back or fails a safe commit**. The real `CoachEngine`/registry is SAR-014; SAR-004 only writes this one note through the injected gateway (fake stack ⇒ canned line, keyless).

**D-E · NB-4 resolved: two narrow audit-state transitions, not a general update.** `CommitRepository` (the group interface, not `AppendOnlyRepository`) gains exactly two single-purpose methods: `markUndone(commitId: string, undoneAt: string): Promise<CommitRecord>` and `markSuperseded(commitId: string): Promise<CommitRecord>`. The impl (`data/repository/commits.ts`) guards a strict state machine: both transition **only from `status:'committed'`**; `markUndone` sets only `status:'undone'` + `undoneAt` (once); `markSuperseded` sets only `status:'superseded'`; any other from-state or any other column mutation ⇒ `RepositoryError`. **Why append-only holds:** the commit *envelope’s lifecycle status* was always designed to move (`commitStatusEnum` ships all three states); its business payload (`draftId/idempotencyKey/kind/summary/undoExpiresAt/createdAt`) stays immutable, and the true audit ledgers (`commit_rows`, both effect tables) remain strictly append-only with no mutation surface. No `update` appears on `AppendOnlyRepository`; nothing else can call these transitions’ SQL path.

**D-F · N-4 resolved: commit/undo are single-flight per user scope.** `CommitService` owns an internal promise-chain mutex (`withLock`): every `commit`/`undoLatest` awaits the previous one on that service instance, so `repos.transaction` is never entered re-entrantly and the `ScopeContext` executor swap stays safe. **Caller contract (documented on `CommitService` and `ScopeContext`):** exactly one `CommitService` per `forUser` scope; never share one scope across concurrent request handlers; a fresh request mints a fresh scope + service via the composition root. Backstops: the DB-level unique `(userId, idempotencyKey)` makes even cross-process races non-duplicating, and a test proves two interleaved `commit()` calls on one service serialize with no executor corruption.

**D-G · XP/game = pure deterministic integer functions in `core/game/`, applied on commit, reversed from the audit record.** `XP_AWARDS: Record<ProposalKind, …>` — **one Terra-authored, Sol-reviewed, tunable constants table (OQ-2 answered: (a))** (flat per-entry award ≈10 XP; minutes-scaled component ≈+1 XP/10 min for `skillSession`/`workout`; fixed level thresholds), `levelForXp(xp)` fixed thresholds, `computeStreak(sortedLocalDates, today, graceDays)` grace-aware and pure, `applyProgress/reverseProgress` producing `domain_progress` patches + `commit_progress_effects` rows. **Reversal replays the recorded effect rows** (`xp − xpDelta`, `level→levelBefore`, `streak→streakBefore`, `minutes − minutesDelta`) — exact, never re-derived — except backdate-affected streaks, which recompute from the remaining logs via the same pure function. No floats, no randomness, no clock reads inside `core/game`. The coach/adaptation/mastery/re-entry mechanics are SAR-014; SAR-004 ships only award-on-commit + reverse-on-undo.

**D-H · Undo + correction/backdate semantics (F3 trust line, F4).** `undoLatest({commitId, now})`: valid **only** for that user’s latest `committed` batch with `now < undoExpiresAt` (5 min); anything else ⇒ typed `UndoNotAvailableError` (expired, superseded, already undone, or not the latest). One compensating `repos.transaction`: creates → `softDelete`; updates → restore `beforeJson` snapshot via typed `update`; reverse progress effects into `plans.progress`; restore plan-item status/source from `commit_plan_effects`; `markUndone(commitId, now)`. Atomic — a mid-undo throw rolls everything back and the batch stays undoable. `UndoResult` lists restored/removed entry ids + the stale capture note id (`stalenessKey:'commit:<id>'` lets SAR-006 filter displays; append-only notes are never mutated). **Corrections** (F4a): always `pending`; on acceptance the dispatch updates the matched entry in place — no duplicate row — and the accepted values persist as `estimated:false, confidenceBps:10000`. **Backdates** (F4b): always `pending`; on acceptance the row is created with the historical `localDate`/`occurredAt`, and the streak is recomputed grace-aware over all logs (recorded as before/after in the progress effect so undo restores it exactly).
