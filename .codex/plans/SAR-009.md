## Locked decisions (sign these off)

**D-A · ONE lens write path: manual tap-to-complete for RULE-FREE habits. [SIGNED — the 2026-07-18 human amendment; supersedes the earlier read-only deferral]**

- **The boundary invariant (state it, test it, enforce it twice):** a habit with ≥1 active `habit_satisfaction_rules` row is **rule-bearing ⇒ refuses manual ticks** (D-E unchanged: wiggle + rule hint; never hand-tickable). A habit with none is **rule-free ⇒ hand-tickable**: its state slot renders a real `<button>` circle (`aria-pressed`, ≥44px hit target) that completes/uncompletes the habit **for today only**. "Active" = a live (non-soft-deleted) rule row, which is exactly what the scoped repository returns.
- **Entry point — REUSE the Done/Skip precedent, NOT the commit service:** new export `setHabitCompletion(habitId: string, next: "done" | "clear")` in `app/(app)/today/actions.ts`, mirroring `setItemStatus` (`actions.ts:13-22`): `"use server"` → runtime-validate both args (server actions are public endpoints) → `getSession()` user-scoped repos → typed write → `revalidatePath("/today")`. The capture path (`core/capture/commit.ts:297-306`) is deliberately **not** reused: `CommitService` exists for proposal batches with XP awards and undo envelopes; a manual tick is a single explicit row toggle — the same class of write as the plan-item Done/Skip. **No XP, no `domain_progress` write, no undo envelope** — the commit transaction stays the single writer of game effects.
- **Toggle semantics — single-row, in-place (forced by the schema, see Current state):** the unique `(userId, habitId, localDate)` index does not exclude tombstones, so the day's row is toggled in place, never soft-deleted:
  - no live row today + `next:"done"` → `repos.habits.logs.create({ habitId, occurredAt: nowIso, localDate, timezone: "UTC", status: "done", source: "manual", note: null })`;
  - live row + `next:"done"` → `repos.habits.logs.update(id, { status: "done", source: "manual" })`;
  - live row + `next:"clear"` → `repos.habits.logs.update(id, { status: "skipped", source: "manual" })` — `skipped` is the status enum's only user-retraction state (`done|partial|skipped|missed`, `contract.ts:68`); the lens renders a rule-free `skipped`/`missed`/`unlogged` row identically as the empty tickable circle, so a cleared tick reads as unlogged;
  - no live row + `next:"clear"` → no-op. `note` is never patched (preserved).
- **Server-side guard (defense in depth, mirrors the D-040 posture):** before any write the action checks `repos.habits.satisfactionRules.list({ habitId })` — any active rule ⇒ refuse (throw); likewise if today's row has `source:"satisfied-by"` ⇒ refuse. Rule-bearing habits are not hand-writable even by a forged request; the UI boundary and the server boundary are the same invariant enforced twice.
- **`localDate` is derived server-side only** — `new Date().toISOString().slice(0,10)`, the same UTC convention as `app/(app)/today/page.tsx:14`. The client never supplies a date: no backdating through this endpoint (backdate remains F4b capture territory).
- **Decision logic is pure and keyless-tested:** `planManualTick({ todayRow, hasActiveRules, next })` in `core/domains/habits.ts` returns `{ op: "create" | "update" | "noop" | "refuse", patch? }`; the server action is a thin executor of that plan. Covered in `tests/habits.test.ts` (D-H).
- **Client behavior:** the tick circle calls the action via `useTransition` (the `NextUpCard.tsx` pattern) with **optimistic** local state; on action failure the optimistic state reverts. **Undo = re-toggle** — symmetric at day granularity, satisfying "every write is undoable". The tick is an explicit user action (never an estimate), so invariant #1 is untouched.
- **`source:"manual"`, not SCREEN-LENSES §3's `source:"tap"`** — pinned by the signed amendment. D-B already buckets every non-satisfied-by source into the `"manual"` display bucket, so the read side is indifferent; at rest the vocabulary is `capture | manual | satisfied-by` (+ seed values).

**D-B · `HabitsView` shape (pure, framework-clean, mirrors `HealthView` discipline).**
```ts
export interface HabitsView {
  localDate: string;
  headline: { done: number; total: number };          // "6 of 8 today" — done = status "done"; total = non-archived habits
  rows: HabitRow[];                                    // checklist, seed order (createdAt)
  heatmap: { weeks: (HeatmapDay | null)[][] };         // current month of localDate, Monday-start, null = pad cell
}
export interface HabitRow {
  habitId: string; name: string;
  streak: number;                                      // grace-aware, per habit (D-C)
  today: "done" | "partial" | "skipped" | "missed" | "unlogged";
  source: "manual" | "satisfied-by" | null;            // today's log.source bucket; "capture"/"tap"/seed → "manual"
  satisfiedBy: null | {                                // non-null iff the habit has ≥1 satisfaction rule
    hint: string;                                      // D-E rule text, e.g. "Satisfies itself from Health — water ≥ 2,000 ml"
    sourceDomain: string;
    todayTotal: number | null;                         // live integer aggregate (null = source rows unavailable)
    targetValue: number | null; targetUnit: string | null; // from the HABIT (drives "2.1/3L" display at the UI edge)
  };
}
export interface HeatmapDay {
  localDate: string; dayOfMonth: number;
  fraction: number;                                    // done-habits / total-habits that day, clamped [0,1] (display-only, like HealthRing.fraction)
  grace: boolean;                                      // hollow ring (D-D)
}
```
`buildHabitsView(input)` takes `{ localDate, habits, logs, rules, ruleTotals }` — all records/ints, no repo, deterministic. Archived habits are excluded everywhere (rows, headline, heatmap denominators). All integer math; fractions only at the display edge. **Tickability is derived, not stored:** a row is hand-tickable iff `satisfiedBy === null` (the D-A boundary — no new field needed). Display mapping for rule-free rows: `today ∈ {done, partial}` → filled circle, tap sends `next:"clear"` (partial counts as filled — it is streak-active per D-C); `today ∈ {skipped, missed, unlogged}` → empty tickable circle, tap sends `next:"done"` — so a D-A cleared tick renders as unlogged.

**D-C · Streak = REUSE `core/game/streak.ts`; grace constant lifted, never duplicated.** Per-habit flame = `computeStreak(activeDates, view.localDate, GRACE_DAYS)` where `activeDates` = that habit's log dates with status `done` or `partial` (`skipped`/`missed` are NOT streak-active — matches F4b: a backdated `skipped` is just a gap the grace window may bridge). `GRACE_DAYS = 1` moves from `core/capture/commit.ts:23` to an export of `core/game/streak.ts`; commit.ts imports it (file-map items 1–2). **No streak logic is written in this ticket** — the lens reuses the exact kernel the commit path uses for `domain_progress`, which is what SCREEN-LENSES §3c means by "grace logic lives in the game layer." The page fetches the user's full `repos.habits.logs.list({})` (dev-scale fine; no aggregate repo methods exist) so streaks see full history, not just the month.

**D-D · Heatmap + the grace ring (deterministic day-level definition). [convention — sign off]** Current month of `localDate`, Monday-start weeks, padded with `null`. Day intensity = `fraction` rendered as `--dom-habits` dot with opacity proportional to fraction (opacity/`strokeDasharray`-style geometry is data-display, not a palette violation — HealthLens precedent); zero-completion days render the faint base dot. **Grace day** (hollow ring, `border` in `--dom-habits`, transparent fill): a day with `fraction === 0` that lies strictly between two days with `fraction > 0` whose gap is `<= GRACE_DAYS + 1` — i.e. a bridged miss, exactly the gap `computeStreak` tolerates. Future days in the month render as empty pad-tone dots. Dots ≥16px with per-day `aria-label` ("Jul 12 — 4 of 8 done" / "grace day, streak protected") per SCREEN-LENSES §5.

**D-E · The satisfied-by REFUSAL affordance (behavioral invariant, not decoration).** A habit with ≥1 `habit_satisfaction_rules` row is a **satisfied-by row**: it never renders a tickable circle — its state slot shows the `⚡ auto from <SourceDomain>` badge plus the live metric (`todayTotal`/`targetValue` `targetUnit`, e.g. "2,100/3,000 ml", int → "2.1/3L" formatting at the UI edge only). Interactions, precisely:
- **Tap (click/keyboard-activate) anywhere on the row** → the row plays one wiggle cycle (translate-x keyframe, duration `--t-fast`, easing `--ease-standard`; under `prefers-reduced-motion` the transform is suppressed and only the hint shows) **and** reveals a transient hint line under the row with the **rule text** — composed by `ruleHint()` from `habit_satisfaction_rules` columns: `"Satisfies itself from Health — water ≥ 2,000 ml"` (`sourceDomain` label + `sourceKind`/`aggregateField` noun + `minimumValue` + `unit`). Auto-dismisses after ~one `--t-hero` beat via a timer; re-tap restarts it.
- **Long-press (pointer down ≥500 ms)** → the same hint, sticky until tapped away — glass-box parity with the capture card's long-press "why". Keyboard/screen-reader equivalence: the row carries `aria-describedby` pointing at the (always-in-DOM, visually-collapsed) rule text, so no gesture is required for a11y.
- **The boundary invariant (revised by the amendment):** rule-bearing ⇒ refuse (this section), rule-free ⇒ manual tick (D-A). `HabitsLens` contains **exactly one** write path — the rule-free tick circle → `setHabitCompletion` — and **no code path that creates or mutates a `habit_logs` row for a rule-bearing habit**; the server guard enforces the same boundary independently of the UI.
