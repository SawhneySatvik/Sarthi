## Locked decisions for this ticket (sign these off)

**D-A · `SkillsView` shape — per-skill mastery summed from sessions, in the read-model.**
```ts
interface SkillsView { skills: SkillTrack[]; }        // ordered: active first (by name), dormant last
interface SkillTrack {
  id: string; name: string;
  masteryMinutes: number;            // sum(skill_sessions.minutes) for THIS skillId — integer, lifetime
  targetMinutes: number | null;      // skills.targetMinutes verbatim
  fraction: number | null;           // masteryMinutes/targetMinutes clamped [0,1]; null when no target
  thresholdHours: 0 | 10 | 100 | 500; // highest of 10/100/500h crossed — DISPLAY-ONLY tier
  nextThresholdHours: 10 | 100 | 500 | null;
  milestones: MilestoneRow[];        // by sortOrder: state ✓ (completedAt≠null) · ▸ (first incomplete) · ○ (rest)
  sessions: SessionRow[];            // most recent first (occurredAt desc), capped at 10; {id, localDate, minutes, source, note, estimated}
  lastSessionLocalDate: string | null;
  dormant: boolean;                  // no session within 14 days of view localDate → card dims (display-only)
}
```
`buildSkillsView({ skills, milestones, sessions, localDate })` takes three raw record arrays (one `list` call each — `repos.skills.skills.list({isArchived:false})`, `milestones.list({})`, `sessions.list({})`) and groups/sums in memory. In-memory lifetime sum is fine at demo scale; a stored per-skill cumulative is a deferred optimization (comment only — invariant #7, no new concept). **`domain_progress.cumulativeMinutes` is never read by this lens.**

**D-B · The mastery counter is the hero — large tabular Display, hours derived from minutes.** Pure helpers in `core/domains/skills.ts`: list card renders `formatMasteryShort(min)` → `H:MM` against `/ 500h` (from `targetMinutes`); the drill hero renders `formatMasteryLong(min)` → `H:MM:00` (seconds fixed at `:00` — they only move when the Focus timer live-tick lands, deferred) in the **largest Display size on the screen, `tabular-nums`, `--dom-skills`-tinted, top of the drill** — nothing else in the drill approaches its scale (the verbatim P3b criterion). The 10/100/500h thresholds are **display-only treatments** (SCREEN-LENSES §4b ~140): a small tier marker + "next: 500h" line derived from `thresholdHours`/`nextThresholdHours`. The *crossing-moment* violet-to-amber pulse + Journey marker fire on a commit event this read-only lens never sees — deferred with the event source. No target (`targetMinutes:null`): hero shows the counter alone, meter hidden.

**D-C · Drill push/return = lens-local state, clean both ways.** `SkillsLens` holds `drillSkillId: string | null`. Tap a track card → drill replaces the list (motion via existing tokens, matching the lens-body swap grammar); a back affordance (`← Skills` chip, top-left) returns `drillSkillId` to `null` with the list's state intact (component stays mounted under `DomainSwitcher`, so scroll/selection survive — "drills push and return cleanly"). No route change; Today remains the route, consistent with `DomainSwitcher`'s existing `useState` pattern. Switching domain chips or re-entering Skills resets to the list. Desktop uses the same push (side-pane deferred, out of scope).

**D-D · Drill content = hero + meter + curriculum + sessions log; read-only.** Curriculum reads `skill_milestones` by `skillId`, sorted by `sortOrder`, glyphs per D-A (`✓/▸/○`, `▸` = first incomplete). **No check-off tap, no `↻ regenerate rest`, no `+ new skill` create** — all belong to the deferred `generate_roadmap`/write ticket (regenerate's "unchecked milestones only" rule, SCREEN-LENSES §6.4, is that ticket's acceptance, not this one's). Sessions log: source-tagged rows (capture/timer/typed from `source`), minutes `tabular-nums`, `~` prefix on `estimated` (the Health glass-box grammar), standard row layout — no edit/delete swipe this ticket. Empty-skills state: the §4c invite card copy ("Name anything — I'll build the road.") rendered static with no create action (creation is the deferred AI path); dormant (14d+) cards dim per D-A's flag.

**D-E · Capture guard = citation, not code.** "No invented skill when the capture proposal requires clarification" is pipeline-enforced at `core/capture/resolve.ts:111–117` + ARCHITECTURE §5.1.7, eval-proven by the `ambiguous-skill` gate-3 fixture (hard `wrongSilentWrites === 0`, SAR-007). SAR-010 changes nothing there; the acceptance run merely re-confirms `pnpm test:eval` stays green.

**D-F · Seed + tests + visual gate.** `scripts/seed-dev.ts` (populated state): set "System design" `targetMinutes: 30000` (500h), seed ~5 milestones (2 completed), ~4 sessions across the past week summing to a readable mastery (e.g. 7,710 min → `128:30`), plus a second skill ("DSA", sparse) left dormant (last session >14d) for the dormant-card state; `SEED_STATE=empty` keeps skills empty for the invite card. `tests/skills-view.test.ts`: per-skill sum isolation (two skills' sessions never cross — the NOT-cumulativeMinutes proof), hours formatting (`H:MM`/`H:MM:00`, integer-only math), threshold tiers at 599/600/601 min boundaries etc., milestone glyph mapping, dormant boundary (14d), null-target handling, empty view. **D-041 visual gate:** `pnpm screenshots` — Skills track list, drill (static counter), empty-invite, dormant card at 390px + desktop, Ember Dark + Light → Sol design review of the PNGs → fix → re-shoot (`.verify/screens/`). The §7 checklist's "live-ticking counter" and "curriculum regenerate" shots are explicitly deferred states.
