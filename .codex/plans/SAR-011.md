## Context

The last capture input mode of the demo spine: a photographed meal or receipt must flow into the SAME parse → route-by-confidence → estimate-deck → typed-commit loop the text path already runs, keyless on the fake vision stack. The pipeline is not rebuilt — SAR-011 is a new *entry ramp* (photo → `VisionProvider.analyze` → `CaptureDraft`) that merges into the existing seam before routing. F5 is the proving gate: receipt snap → N pending transaction cards → explicit `Accept all` → one commit batch → Money lens moves.

Invariants touched: **#1** — photo-derived values NEVER auto-write: the meal result is forced `estimated:true` by the mapper, and a new routing reason (photo evidence ⇒ pending, §5.1 rule 4) guarantees every photo-derived proposal — including explicit receipt amounts — routes `pending`; the commit route's existing auto-mode re-route (D-040) enforces it server-side with no extra code. **#2** — receipt `amountPaise` and meal `kcal`/`grams` are integers end-to-end; the mapper does passthrough only, no arithmetic, no float. **#3** — the whole path runs on `FakeVisionProvider` (deterministic canned meal/receipt), zero keys; `VISION_PROVIDER=fake` is already the default. **#4** — the only new UI (camera input, photo thumbnail chip) is tokens-only; no amber. **#5/#6** — typed writes go through the untouched `resolveProposal` → `CommitService` path; no generic parsed blob persists (the draft lives only in client state, exactly like the text path). **#9** — `core/capture/vision.ts` imports zod + core types only; `FormData`/file handling stays in the route handler.

## Locked decisions for this ticket (sign these off)

**D-A · Vision result contract + mapper live in core; the provider stays schema-generic.**
`core/capture/vision.ts` defines:
```ts
visionMealResultSchema    // { kind:'meal', confidenceBps, meal:{ kcal, proteinGrams|null, carbsGrams|null, fatGrams|null, items:[{name,quantity,unit}], note|null } }
visionReceiptResultSchema // { kind:'receipt', confidenceBps, merchant|null, purchasedLocalDate|null, transactions:[{ amountPaise, direction, categoryName, merchant|null, note|null }] }
visionResultSchema        // discriminatedUnion('kind', [meal, receipt])
```
All quantities non-negative integers (paise/kcal/grams — invariant #2). `parsePhoto({images, timezone, capturedAt, caption?}, vision)` mirrors `parseDump` exactly: `vision.analyze({images, schema: visionResultSchema, prompt, tier:'deep'})`, defensive `safeParse`, any throw/invalid object ⇒ `{ok:false, retryable:true}` — **zero rows, zero outbox** (`provider-failure` grammar). `draftFromVisionResult` is a PURE function → `CaptureDraft`: `source:'photo'`, `rawText` = caption or `"Meal photo"`/`"Receipt photo"`, `transcriptConfidenceBps:null`, deterministic ids (`photo-<uuid>` draft, `<draftId>-meal` / `<draftId>-txn-N` proposals), `localDate` computed from `capturedAt` in the capture timezone via `Intl` (pure helper; the standing UTC→local follow-up notes this as the first correct-by-construction site). Meal ⇒ ONE meal proposal **forced `estimated:true`** with a why-basis "estimated from a meal photo" + portion assumption; receipt ⇒ N transaction proposals `estimated:false` (printed values), `intent:'create'`, receipt merchant/note carried into payloads. `providers/fake/fixtures.ts` meal/receipt fixtures are updated to CONFORM (add `kind`, structure the meal items, add receipt `confidenceBps: 8600` + `purchasedLocalDate: null`); amounts/macros unchanged, `FAKE_FIXTURE_VERSION` unchanged, `FakeVisionProvider` logic untouched.

**D-B · Photo-derived ⇒ pending, keyed on non-empty `evidenceRefs` — the ticket's ONLY pipeline edit.**
The mapper attaches one `DraftEvidenceRef` `{ref:'photo:<draftId>', mimeType, sha256:null, caption}` to the draft AND to every derived proposal. `routeProposal` gains one reason: `evidenceRefs.length > 0` ⇒ `"photo-derived value requires confirmation"` (§5.1 rule 4 verbatim). Consequences, all free: the client `routeDraft` decks every photo proposal; the commit route's auto-mode re-route (D-040, `commit/route.ts:65`) makes it **server-enforced** — a client that mislabels a receipt txn as `auto` gets it back `unresolved`, never written; `prepareDraft` in the eval behaves identically. Receipt txns keep an HONEST 8600 bps (not gamed under a threshold): pending comes from the evidence rule, and 8600 ≥ 8000 keeps the batch **Accept-all eligible** (F5's "all ≥.8"). Every pre-existing text/voice proposal has empty `evidenceRefs` ⇒ zero regression (F3 eval re-run proves it). Accept-all remains ONE explicit user action → ONE commit batch → idempotent on retry (existing `idempotencyKey` replay) → one 5-min undo.

**D-C · Transport seam = a NEW sibling route, `POST /api/capture/parse-photo`; the text route is untouched.**
Multipart `FormData`: `photo` (File), `timezone`, optional `caption`. The handler is a thin adapter exactly like `parse/route.ts`: reject missing/oversized photo (cap **8 MB** ⇒ 413) or non-`image/jpeg|png|webp` mime ⇒ 400; bytes → `Uint8Array` → `ImageInput{bytes, mimeType, filename}` (filename passed through — D-E) → `getSession().vision` → `parsePhoto` → same `{ok:true, draft}` / retryable 502 shape, so `CaptureSheet`'s post-parse code path is byte-for-byte shared. `app/lib/session.ts` adds `vision: createVisionProvider(config.visionProvider)` beside `llm` — the composition root stays the only place a provider is constructed. The photo bytes live only in request memory; nothing is written to disk/DB/storage.

**D-D · Client: enable the existing camera affordance; the sheet gains a photo mode, nothing else.**
`CaptureLauncher`: the disabled camera button becomes live — it triggers a hidden `<input type="file" accept="image/jpeg,image/png,image/webp" capture="environment">`; a selected file opens the sheet with a session union `{mode:'text', text} | {mode:'photo', file}` (current visibility swap send↔camera kept; mic/text paths untouched). `CaptureSheet`: on photo mode the parsing effect calls `parsePhoto(file, tz)` instead of `parseText`; the pinned-quote slot renders a small thumbnail chip (client-only `URL.createObjectURL`, revoked on close — the preview never uploads or persists) + the draft's `rawText` label. Everything from `routeDraft` onward — strip (empty for photo, correctly: nothing auto-writes), questions, deck, accept/Accept-all/edit/why, fan-out, undo — is the UNCHANGED existing code. Receipt merchant/date surface per-card (payload merchant + the existing date handling), satisfying F5's intent without a new strip variant; a richer receipt header is deferred polish. Tokens-only; 44px targets; no amber.

**D-E · Fake meal/receipt discrimination stays filename/prompt-keyed — an accepted keyless-stack limitation.**
`FakeVisionProvider` keeps its existing rule (filename or prompt contains "receipt" ⇒ receipt fixture, else meal). Deterministic and key-free; demo/tests/screenshots select via named files (`meal.jpg` / `receipt.jpg` picked from the gallery). A live camera snap on the FAKE stack therefore lands as a meal — acceptable: content-based discrimination is precisely the real vision adapter's job (out of scope, a later ticket). No chooser UI is added. **This limitation needs explicit sign-off.**

**D-F · Fixtures, eval, and the visual gate.**
`tests/fixtures/capture/index.ts` adds `receiptBatchFixture` whose draft is built **through the real mapper** from the fake receipt fixture — `expected: {auto: [], pending: [both txns]}` ("pending cards; Accept-all only through explicit action", §8.1). The eval (extend `f3-gate` or a sibling `f5-receipt` file, same harness) proves keylessly: (1) `FakeVisionProvider` → `parsePhoto` → mapper → `prepareDraft` yields ZERO auto rows for both meal and receipt photos (`wrongSilentWrites === 0` stays a hard aggregate — the meal photo now travels the REAL vision path, upgrading the synthesized gate-3 fixture, which is kept as-is for gate continuity); (2) explicit Accept-all commits exactly 2 typed `transactions` rows (integer paise) in one batch — with "Transport" seeded in-test; (3) replaying the commit with the same `idempotencyKey` returns the original result, still 2 rows — "writes once, never duplicates on retry"; (4) `undoLatest` restores. `tests/capture-vision.test.ts` unit-covers the mapper (integer passthrough, forced `estimated:true` meal, evidence refs present, localDate/timezone), the routing rule (photo ⇒ pending even at 9800 bps `estimated:false`; empty-refs proposals unaffected), and `parsePhoto` failure ⇒ retryable + zero side effects. **D-041 visual gate:** `pnpm screenshots` — capture bar with live camera affordance · photo-parsing (thumbnail + shimmer) · meal estimate card · receipt-batch deck with Accept-all · post-Accept-all fan-out, at 390px + desktop, Ember Dark + Light (photo files synthesized in-script from a base64 constant + Playwright `setInputFiles` — no committed binaries) → Sol design review → fix → re-shoot into `.verify/screens/`.
