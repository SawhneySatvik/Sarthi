## Context

The production new-account path: a fresh user is gated to `/onboarding`, answers 6 core questions (~2 min), watches four spines generate glass-box from those answers (deep tier, through the SAME provider gateway the capture parse uses, keyless on the fake adapter), edits/trims four confirm cards, and taps **one** button that performs the ticket's **single atomic write** — profile + plans + habits + skills + money scaffolding — flipping `onboardingStatus → 'complete'`. Optional DETAIL sections sharpen the profile after; every skip enqueues a `profile_gap` for the (SAR-014) coach to backfill. Nothing persists before the D-accept tap except a local client draft. Moves **F1** end-to-end.

Invariants touched: **#1** — the onboarding write is USER-CONFIRMED at D: the swipe-gate philosophy extends here verbatim ("Nothing is created until this tap", SCREEN-ONBOARDING §6:61); spine values are plan *definitions* the user reviews row-by-row, never estimated *entries*, and zero rows exist before the tap (F1 exit criterion :16). **#2** — every persisted quantity is an integer: `heightCm`/`weightGrams`/`wakeTimeMinutes`/`sleepTimeMinutes`/`timeBudgetMinutes`/`screenTimeMinutes` (contract.ts:271–291), `limitPaise`/`amountPaise` (:557,:609), plan `targetValue` ints (:1329); the imperial toggle converts at the input boundary and stores metric ints (§4 B3:44). **#3** — spine generation is a real deep-tier `generateObject` per domain through the injected `LlmGateway` with a deterministic fake adapter; the whole flow runs keyless. **#4** — tokens-only; `--energy` amber appears ONLY on the CORE progress hairline (§1:24) and the earned `Looks right — start Day 1` CTA (§6:60) — both explicitly sanctioned by the screen doc and this sign-off. **#5/#6** — every write goes through the scoped typed repositories (`ScopedEntityRepository`, core/contracts/repositories.ts:149–155); no driver touch, no generic blob. **#9** — all onboarding business logic (answer contract, spine derivation, accept service) lives in `core/onboarding/*` with zod + core types only. **#10** — the demo path stays free; the demo-seed gesture is keyless and judge-invokable.

## Locked decisions for this ticket (sign these off)

**D-A · The entry gate lives in the `(app)` shell layout; the seed keeps Today working.**
`app/(app)/layout.tsx` becomes the single gate: read the profile singleton via `repos.profile.profiles.byId(user.userId)` (userId-keyed per base.ts:126); a missing row (fresh DB — today's reality, seed-dev.ts creates none) or any status ≠ `'complete'` redirects to `/onboarding`. `/` → `/today` (app/page.tsx:4) then gates for free; API routes stay ungated. The keyless single-dev-user coexistence: `scripts/seed-dev.ts` writes a `complete` profile in `populated|empty|alldone`, so every existing demo/screenshot state renders exactly as before; the new `SEED_STATE=fresh` is the only state that lands in onboarding.

**D-B · `onboardingStatus` flips to `'complete'` INSIDE the D-accept transaction; the commit signal is the flip.**
Before accept there is NO profile row at all — the local draft (versioned localStorage, PII-bearing, cleared on accept) is the only persistence, which makes "zero writes before D-accept" (F1:16) structurally true rather than policed. After accept, E→F→G continue client-side within the same flow session; a HARD reload of `/onboarding` with a `complete` profile redirects to `/today` (acceptable: all five E gaps are already enqueued — the backfill covers whatever the reload skipped; `onboardingStep` records the furthest phase reached, set 6 at accept and bumped by E/F patches).

**D-C · Keyless Phase A renders NO sign-in affordance.**
The "I have an account" quiet link (§3:36) renders only when the server-passed auth mode ≠ `'local'` — the prop seam exists now, the affordance appears when SAR-021 lands Supabase. Nothing dead ships in the demo.

**D-D · B-screen voice-fill = text → fast-tier `generateObject` through the gateway; audio is SAR-013.**
The mic affordance opens a "say it or type it" input; its text posts to `/api/onboarding/fill` with the QUESTION's field schema (`telemetry.operation:'onboarding-fill'`, tier `fast`). The fake returns deterministic canned fills per question key. Parsed fields are shown for explicit confirmation before entering the draft (§2:30 "user confirms"); failure ⇒ empty field + chip pulse, zero side effects. This upgrades P4's "decorative" mic (:228) to the locked functional scope without touching SAR-013's audio contract.

**D-E · The spine contract: per-domain zod schemas + a deterministic answer-derived builder in `core/onboarding/spine.ts`.**
One schema per domain, discriminated on `domain`, every quantity `z.number().int()`:
```ts
healthSpineSchema  // { domain:'health', headerLine, targets:[{kind:'target'|'checkin', title, targetValue|null, targetUnit|null}] }  — kcal/waterMl/workout-minutes targets
habitsSpineSchema  // { domain:'habits', headerLine, habits:[{name, cadence, difficulty, targetValue|null, targetUnit|null, satisfactionRule|null}], items:[…] }
moneySpineSchema   // { domain:'money',  headerLine, categories:[{name, kind, monthlyLimitPaise|null}], items:[…] }
skillsSpineSchema  // { domain:'skills', headerLine, skill:{name, targetMinutes}, milestones:[label…], items:[…] }
```
`deriveSpine(domain, answers)` is pure and glass-box: session/target minutes scale from `timeBudgetMinutes`, cadence/timing from `dayShape`+wake/sleep, selection from the B5 goal chips, the named skill verbatim, the under-18 branch (§10:96) switches Health to conservative defaults with no weight-loss framing — and it composes `headerLine` from the same inputs (*"Based on your 30 minutes and 9–5 — here's a start."*), so "confirm cards clearly derive from the answers" is a computed property, not copywriting. `generateSpine` calls the gateway with the answers in a fenced JSON envelope; `FakeLlmGateway` parses that envelope and runs `deriveSpine` (providers already import core — same direction as fake→core/contracts today), so the keyless spines genuinely vary with the answers. Real providers (google/openai) flow through the existing `AiSdkLlmGateway` untouched. The envelope format is locked by a unit test so fake and prompt can't drift.

**D-F · The D-accept write: one service, one transaction, idempotent, ordered.**
`acceptOnboarding` (core/onboarding/accept.ts) — single-flight per scope; guard first: an existing `complete` profile ⇒ replay no-op summary (accepting twice never double-writes). Then ONE `repos.transaction` (pattern: commit.ts:482) in dependency order, all through scoped typed repos:
&nbsp;&nbsp;**a.** `profile.profiles.create` — every B answer (metric ints), `unitSystem`, defaults (`theme:'ember'`, `plan:'free'`), `onboardingStatus:'complete'`, `onboardingStep:6` — the flip IS the commit signal;
&nbsp;&nbsp;**b.** money selected ⇒ `money.categories` create-if-missing by `(name,kind)` case-insensitive (the seedCanonicalEntities idiom, data/seed/canonical.ts:16–19 — this also absorbs a dev DB that already carries canonical entities, unique-constraint-safe) + `money.budgets` rows (`limitPaise` int) for spine categories with a limit;
&nbsp;&nbsp;**c.** habits selected ⇒ `habits.habits` create-if-missing by name + `habits.satisfactionRules` for spine rules;
&nbsp;&nbsp;**d.** skills selected ⇒ `skills.skills` create-if-missing + `skills.milestones` (ordered `sortOrder`);
&nbsp;&nbsp;**e.** one `plans.arcs` per SELECTED domain (`dayNumber:1`, `startDate:` today, `status:'active'`) + its `plans.items` (Day-1 `localDate`, `kind` from `planItemKindEnum`, integer `targetValue`, `linkedHabitId`/`linkedSkillId` wired to the rows just created);
&nbsp;&nbsp;**f.** `plans.progress` zeroed rows (`overall` + each selected domain: xp 0, level 1, streak 0 — no unearned XP, no amber) + `plans.dayOneSnapshots` per selected domain (zeroed `statsJson`; lookup-first against unique `(userId,domain)`);

The client sends the EDITED spines + answers; the server re-validates everything (zod ints — a float dies at the boundary) and derives nothing new. No `CommitService`, no undo envelope (rationale in Current state); everything created is user-confirmed and editable.
