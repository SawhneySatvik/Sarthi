## Outcome

Introduce one framework-clean, registry-driven `CoachEngine` that derives its grounding from
the four typed stores, creates deterministic fake-stack capture/daily/weekly responses, and
manages glass-box plan adaptations. A daily or weekly brief is de-duplicated by a signed
evidence/staleness key; a plan change first persists as a visible `proposed` adaptation. Only a
deliberate **Keep** mutates the typed `plan_items` row through `CommitService`; **Revert** of a
proposal never changes the plan. The existing game kernel remains the source of XP/levels/streaks;
SAR-014 adds one deterministic read model for mastery, plan-effect, re-entry, and evidence counts.

SAR-014 provides server endpoints and read models for F2/F6/F7/F9. The Coach reading-room UI,
adaptation sheet, brief presentation, and screenshots are deliberately SAR-015 work.

## Locked interpretations

- **F9 correction — architecture wins.** Re-entry (three or more inactive local days) creates or
  reuses a visible *proposed* lightening adaptation. It does **not** silently alter a plan. Today
  shows the lighter spine only after the user taps **Keep**. Terra updates the stale F9 and
  `SCREEN-COACH` “auto-lightened” wording as a documentation correction in the ticket docs commit;
  it is not a new product decision.
- **Single-level undo holds for Keep.** A Keep is a `CommitService` plan-patch commit, with the
  same five-minute latest-batch undo envelope as capture. The adaptation records its applied
  commit id so a subsequent generic undo restores both the `plan_items` snapshot and the
  adaptation's coherent visible state (`reverted`), rather than leaving a misleading kept chip.
  This is a small typed schema addition (`adaptations.appliedCommitId: string | null`), not a
  generic payload or a new domain concept.
- **Revert before Keep is non-mutating.** It changes only the adaptation status and timestamp;
  the `plan_items` row and all game effects stay exactly as they were. A stale/foreign/non-proposed
  adaptation fails closed. The ticket does not add an adaptation-history UI.
- **No fifth coach.** The registry has exactly `health`, `money`, `habits`, and `skills` entries.
  Overall summaries compose those four contexts; `overall` is never a `DomainSpec`.
- **Game metrics are derived, not duplicated.** Existing persisted `domain_progress` remains the
  authoritative XP/level/streak audit state. Mastery is summed integer `skill_sessions.minutes`
  per D-044; plan effects, inactive days, and evidence totals derive from typed rows. No new game
  table or float unit is introduced.
- **No unrelated work.** Do not touch the pending `.gitignore` diff. Do not build the Coach tab,
  streaming UI, photo/audio persistence, real provider wiring, billing/auth, or SAR-015 screens.

## Build shape

1. **Coach contracts, evidence, and four-entry registry**
   - Add `core/coach/` with explicit DTOs for `DateRange`, per-domain context, grounded
     `CoachEvidence`, staleness/evidence fingerprints, brief outputs, plan-patch adaptations, and
     the `CoachEngine` port. Keep all modules framework-, driver-, and provider-implementation
     clean; inject `UserScopedRepositories`, `LlmGateway`, and `CommitService` at construction.
   - Implement exactly four `DomainSpec` entries. Each uses its domain's typed repositories only
     and produces a bounded, deterministic context/evidence list. No domain-specific engine,
     router, or generic table/payload persistence path is allowed.
   - Produce stable daily and weekly staleness keys from scope, local date/window, and the sorted
     typed-evidence fingerprint. Reuse an existing `(scope, stalenessKey)` note; create a new note
     only when evidence changes. Capture lines stay fast; daily/weekly briefs use deep; Ask stays
     outside the persisted thread and is fast unless its explicit plan/money classifier escalates.
   - Consume still-open onboarding `profile_gaps` in the daily brief's grounded context. The engine
     may surface one next gap but must not answer, close, or invent profile data.

2. **Deterministic game and re-entry read models**
   - Add pure `core/game` helpers/read models that expose existing XP/level/streak state alongside
     per-skill mastery (integer summed minutes), typed plan-effect counts, evidence counts, and
     grace-aware inactive-day/re-entry eligibility. They accept records/clock input; no DB, clock,
     framework, or provider import is permitted.
   - Derive re-entry candidates deterministically from typed plan/progress rows. A candidate has a
     `CommitRowSnapshot` of one eligible `planItem` before/after; numeric targets are reduced using
     integer arithmetic only. When no safe eligible item exists, return no adaptation rather than
     inventing a target or rewriting a title/status.
   - Reuse an open equivalent proposal on repeated checks, so refresh/retry cannot create an
     adaptation pile. Until Keep, all plan rows, XP, streaks, and plan effects remain unchanged.

3. **Typed adaptation commits and schema parity**
   - Extend the closed schema contract plus SQLite/Postgres declarations and migration/parity tests
     with nullable `adaptations.appliedCommitId`. Validate it as a concrete UUID/text identity;
     it links a kept adaptation to its exact plan-patch commit and never carries a generic object.
   - Extend `CommitService` with a typed adaptation-plan-patch operation. Inside one scoped
     transaction it validates the proposed adaptation's snapshots against its owned `planItem`,
     supersedes the prior undo batch, writes a `tool` commit envelope plus exact `commit_rows`
     before/after snapshots, applies the typed plan-item patch, and marks the adaptation kept with
     `appliedCommitId`/timestamp. No capture proposal dispatcher is reused or weakened.
   - Extend undo to recognize that linkage: undoing the latest Keep restores the plan snapshot and
     atomically marks that adaptation reverted. Revert while still proposed writes only the
     adaptation lifecycle fields; it never creates a plan commit or modifies `plan_items`.
   - Preserve tenant scoping, idempotency, single-flight sequencing, immutable audit ledgers, and
     the existing capture undo behavior. A failed validation or transaction leaves no partial
     plan/adaptation/commit state.

4. **Engine composition and typed Coach API**
   - Add thin authenticated routes under `app/api/coach/` for brief generation, session-only ask,
     re-entry/adaptation proposal lookup, and explicit Keep/Revert resolution. Every boundary Zod
     validates input, gets the scoped session, and delegates to the engine; clients cannot submit
     arbitrary `beforeJson`/`afterJson`, user ids, or raw repository filters.
   - Extend the server-side Today/Coach accessor only as needed to expose the current daily note,
     deterministic re-entry proposal, and game summary to SAR-015. Do not build the reading-room
     JSX or change the existing Today visual layout in this ticket.
   - Keep `FakeLlmGateway` keyless and fetch-free. Add deterministic daily/weekly/ask/adaptation
     fixtures keyed by the existing telemetry operations; fake output must validate through the
     same Zod contracts as live output.

5. **Tests, eval seam, and documentation**
   - Add focused keyless tests for: exactly four registry entries; typed context/evidence and
     deterministic staleness reuse/regeneration; fast/deep routing; profile-gap inclusion; no
     network or keys on fake; mastery/evidence/re-entry derivation; and the `adaptationSanityRate`
     numerator/denominator seam.
   - Exercise adaptation safety against real in-memory SQLite: proposed → Keep creates one
     plan-patch commit and exact snapshots; replay/concurrency cannot duplicate it; proposed →
     Revert preserves the plan; generic undo of the latest Keep restores the plan and coherent
     adaptation status; foreign/stale/malformed requests fail with zero writes.
   - Run `pnpm check`, `pnpm build`, and `.codex/hooks/check-invariants.sh`. SAR-014 has no new
     visual surface; SAR-015 owns the D-041 Coach screenshot set. If Terra changes any existing
     rendered surface while exposing the API, capture the affected 390px + desktop regression
     evidence before acceptance.
   - In the documentation commit, mark SAR-014 landed only after the above gate, record any
     `adaptationSanityRate` coverage, and correct F9/`SCREEN-COACH` re-entry wording to match the
     locked no-silent-write rule.

## Acceptance and verification

- Exactly four `DomainSpec` entries feed one `CoachEngine`; no domain-specific coach
  orchestration exists.
- Fake stack daily/weekly/capture/ask outcomes are deterministic and keyless. Daily/weekly notes
  carry typed evidence and obey scope-plus-staleness uniqueness.
- An adaptation is visible and `proposed` before it can affect a plan. Keep is the only action
  that applies its typed snapshot through `CommitService`; Revert of a proposal preserves the
  plan. Keep remains single-level undoable without corrupting adaptation state.
- XP, levels, streaks, skill mastery, typed plan effects, evidence counts, and re-entry eligibility
  are deterministic from the signed typed-record inputs; money/quantity math remains integer-only.
- F2, F6, F7, and F9 have engine/API support. SAR-015 alone turns those contracts into the Coach
  reading room and performs its screenshot gate.
